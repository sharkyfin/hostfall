# Терминальный срез: три узла, одна цепочка

## WS-07 — источник

ps → inspect PID → crontab -l. Остановка cache-sync до исправления crontab вызывает настоящий повторный запуск и новый PID. Игрок может закомментировать строку в редакторе, убрать её через grep с установкой нового crontab либо удалить задания целиком. После устранения источника и процесса открывается ssh edge01.

## EDGE-01 — алгоритм

cat /etc/egress/contract.txt → edit /etc/egress/filter.js. Игрок пишет JS-функцию, запускает тест черновика или node FILE --test. Начальное return true проходит только 5/11. Правильные разные алгоритмы проходят 11/11; правило по нескольким известным id не проходит новые пакеты. Сохранить файл, затем curl -X POST /api/firewall --data @/etc/egress/filter.js. При корректной политике открывается core01; ХОР отвечает на отсечение голоса.

## CORE-01 — коммутация и порядок

Прочитать заявку и журнал ХОРА. patch открывает входы и выходы. replication → vault, operator → console, care → hospital; сохранить, применить запросом. Альтернатива — написать тот же конфигурационный JSON руками. Остановка chorus раньше изоляции запускает внешнего лидера; после — действительно останавливает сервис. POST /api/commit отправляет отзыв по сохранённому независимому каналу.

## Проверенные варианты

- Редактор crontab + найденный PID + JS-словарь разрешённых пар + patch → чистый финал, 0 секунд потери care.
- Конвейер grep / crontab + альтернативные JS-условия → те же правильные последствия.
- Плохой фильтр запрещает care/control, его можно исправить; ущерб остаётся для costly-финала.
- Остановка лидера с global → peer-перезапуск и ускоренное слияние.
- Бездействие wait после обнаружения внешней сети → assimilated, HUMAN / H-0.
- Повторное включение задания WS после очистки → финальная проверка отказывает.
